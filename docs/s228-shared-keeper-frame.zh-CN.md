# S228：共享比赛到既有门将策略的只读状态适配

## 本轮完成的范围

新增 `providers/g1/keeper_frame.py`。它把共享球场中按名字寻址的一名 G1 和
足球，投影到旧单门将控制器使用的规范场景：门将锚点 `(4.52, 0)`，面向
负 X，43 维 qpos、41 维 qvel，保持既有 29 关节顺序。

这不是又训练了一轮近球残差，也不是把旧策略强行加到比赛控制器上。
适配器只产生不可写、脱离原数据的状态快照，不写原世界、力矩、控制目标，
不加载硬件，不授予模型控制权。

## 解决的具体接入问题

- 旧门将代码直接使用 `qpos[36:43]` 等单机器人下标；共享八机器人场景的
  同一球、同一 G1 地址不相同。新实现按根关节、29 个标准关节及球的名字
  寻址，缺失关节或类型错误拒绝。
- 红蓝门将朝向相反。这里使用正常刚体旋转而非左右反射，保持手脚解剖
  身份和关节角不变；位置与世界线速度转换到规范坐标。
- MuJoCo 自由关节角速度使用身体局部坐标，不能跟世界线速度一起旋转。
  本实现保留该局部角速度，并用真实刚体速度计算验证。
- 拒绝非法形状、非有限状态及非单位姿态四元数；快照不能通过设置
  writeable 标记重新获得写权限。

## 实际验证

在实际八 G1 MuJoCo 模型中，分别核验红蓝门将与规范单 G1 模型：

1. 躯干、左右踝、左右腕的前向运动学位置误差不超过 `1e-10 m`。
2. 同一身体部位的世界空间速度转换后误差不超过 `1e-10`。
3. 无接触、相同重力条件下，各推进一个真实物理步，转换后的 qpos/qvel
   与单 G1 模型误差不超过 `1e-8`。这不是有接触场景的动力学等价证明。
4. 旧定向扑救控制器的 89 维观测函数直接接受快照；其结果与规范单模型
   观测一致，测试容差 `1e-7`。
5. 读取已有 S44 v9 数值 checkpoint，使用 `weights_only=True`，在 CPU 上
   做只读 actor 前向：两个输入路径产生相同的有限 30 维输出。没有把这些
   输出施加给机器人，也未把这个旧候选当作合格冠军。
6. 验证映射不改变共享场景原始 qpos/qvel。

原始测试记录在 `$ROSCLAW_SOCCER_EVIDENCE/s228-keeper-frame-contract/`。
checkpoint 哈希记录在带 actor 前向的 JUnit 属性中。定向测试 3 passed；
全量回归 1174 passed、13 skipped、11 个既有外部历史证据绑定失败；ruff、
mypy（406 个源文件）通过。

## 未完成的部分与下一步

这是状态与观测输入适配层，不是已经完成的门将控制接管。本轮没有新训练，
没有新的扑救成功率，也没有产生声称门将变强的运动视频。上一轮视频仍是
诊断基线，不能用它冒充本适配器带来的动作提升。

后续还必须验证模型/身体哈希、动作缩放、解码器和步行策略的组合、每台
门将各自的循环状态、因果来球触发、激活/退出和恢复边界；然后才能在共享
世界里做有接触的双边射门扑救试验，输出对应视频。
