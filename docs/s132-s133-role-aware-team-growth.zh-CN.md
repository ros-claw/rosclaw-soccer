# S132–S133：角色自模型、团队归因与传接球握手闭环

## 结论先行

本阶段完成了“每台机器人知道自己是谁、会什么、和谁合作、和谁对抗”的工程基础，并把
它接到了已有三台 G1 的真实 MuJoCo 轨迹上。角色审计通过，组织者局部传球 discovery
也在修正后的完整冻结链上通过；但新鲜团队协同仍未通过，因此没有晋升策略，也没有制作
宣传视频。

最重要的技术结论不是又找到一组常数，而是定位出下一处真正瓶颈：组织者把球送进宽松的
可接球域，并不保证终结者能按指定脚完成射门；在两个困难球位上扫描接球者 ±0.08 秒的
固定启动偏移，仍然是 0/2 严格完整链。下一代需要基于实时来球状态连续决定接触相位的
`RECEIVE` actor，而不是更多回合前常数。

## 1. 每个智能体现在知道什么

新增的角色自模型把身份、角色、队友、对手、技能产物、证据、私有失败记忆和允许的高层
意图绑定为不可变内容哈希：

| 角色 | 核心技能 | 允许的典型意图 | 当前三 G1 场景 |
|---|---|---|---|
| Playmaker / 组织者 | lead pass、first touch、recovery | PASS、RECEIVE、CARRY、SUPPORT | `red.playmaker` |
| Finisher / 终结者 | first touch、finishing、recovery | RECEIVE、RUN IN BEHIND、SHOOT | `red.finisher` |
| Goalkeeper / 门将 | positioning、save、recovery | COVER、SAVE、DISTRIBUTE | `blue.goalkeeper` |
| Defender / 后卫 | marking、interception、recovery | PRESS、COVER、INTERCEPT | 已有契约，尚未加入本轮三机证据 |

角色不是文字标签。运行前会校验：

- 一个门将不能用 `SAVE` 技能提交 `SHOOT`；
- `PASS` 的目标必须是声明过的队友；
- `PRESS/INTERCEPT` 的目标必须是声明过的对手；
- 每个观测必须分别列出队友状态和对手状态，禁止交换身份；
- 同一支队伍同一协调帧只能有一个持球动作所有者；
- 每个角色拥有独立失败记忆命名空间，避免把别人的失败写进自己的技能成长。

这层只输出高层意图，不输出关节力矩，不授权硬件，激活上限固定为 `SIM_ONLY`。

## 2. 团队协作不再是单方面“传一下”

`PassReceiveHandshake` 把一次传接球定义为两名队友共同签署的协议：

1. 组织者提交 `PASS + LEAD_PASS + receiver_id`；
2. 终结者以同一个协调时钟提交 `RECEIVE/FIRST_TOUCH`；
3. 双方绑定各自 self-model 和 egocentric observation 哈希；
4. 协议提交目标点、预计到达时间、接球者就绪起止窗口和预计球速；
5. 预计到达必须落在接球者明确接受的窗口中；
6. 没有唯一握手、接球者未确认或出现孤立握手时，整个团队协调帧拒绝。

门将不是背景物体。它属于另一支队伍，观察红队为对手，并通过 `COVER/SAVE` 给进攻链
提供真实对抗结果。团队结果可以共享，但角色技能成绩分别记账。

## 5. 固定接球时序为什么仍然失败

在 `s133-team-pass-handshake-discovery-v2-contract-hardened` 中，冻结组织者的上述动作、
终结者完整神经接触技能和门将策略，只对接球启动做
`-0.08/-0.04/0/+0.04/+0.08 s` 扫描，共 10 条轨迹。v2 同时把传球目标必须为 xyz
三维向量纳入运行时契约。

报告哈希：

`sha256:714e50b5f805ab20d4e96ba3c60e8684a9fb6c247732a02c63e1352cdaef0a14`

结果为可完整验证的 `REJECTED_TEAM_PASS_HANDSHAKE_DISCOVERY`：

| 指标 | 结果 |
|---|---:|
| 安全 | 10/10 |
| 神经终结者实际激活 | 10/10 |
| 老师/脚本接触介入 | 0/10 |
| 严格传球—右脚射门完整链 | 0/10 |
| 恢复上下文 | 0/2 |
| 进球 / 门将扑救 | 0 / 0 |

这排除了“只差固定启动 40–80 ms”的简单解释。当前来球在毫米级初始球位变化下会发生
接触分岔，球速、到达位置和到达时间共同变化。终结者只在回合前选择固定接触计划，无法
在球真正到来时重新对齐。

## 6. Stability–Plasticity 的处理

本阶段没有让三个机器人一起更新：

- 单体训练时只开放一个角色技能，队友与对手策略以内容哈希冻结；
- 团队时序训练只开放 handshake，三套低层策略全部冻结；
- 成功和失败轨迹都保留，失败用于排斥不可靠动作邻域；
- discovery、distillation、新鲜 holdout 分区分离；
- 任何报告都不自动晋升，且所有新产物保持 `SIM_ONLY`；
- 验证器从原始 result/quality、轨迹文件哈希和预注册 request 重算门控，允许“证据有效但
  实验失败”，拒绝把 REJECTED 改写成 PASS。

这就是当前闭环中的稳定性：旧的 S130 终结者和门将能力不被组织者训练覆盖；可塑性则
来自角色私有失败课程与团队握手课程。

## 7. 下一阶段 S134：运行时 RECEIVE actor

下一阶段不再扩大固定参数网格，重点实现终结者的实时接球小脑：

1. 每个控制帧读取终结者自我状态、球相对位置/速度、预计到达时间、支撑脚、骨盆姿态和
   当前策略相位；不使用像素和仿真特权标签。
2. actor 只在有限范围输出 `hold/advance/keep` 接触相位与小幅站位残差；禁止改 qpos、
   改球状态或直接注入球力。
3. 组织者继续提交目标和预计到达分布，终结者基于实测状态持续更新 readiness window，
   双方通过同一 handshake commitment 对齐。
4. 奖励分解为：团队明确结果 + 组织者交付 + 终结者指定脚接触 + 门将真实扑救 − 稳定性
   代价；反事实只给真正改变的模块记信用。
5. 先在本轮两类失败周围做密集 development，再生成不相交的新鲜球位做主运行/重放；
   至少安全全通过、严格链显著提升后才允许下一次视频。

## 8. 本阶段证据边界

- 物理权威：CPU MuJoCo；
- 激活上限：`SIM_ONLY`；
- 无 ROS topic、DDS、串口、CAN、vendor SDK 或真实硬件动作；
- 像素不参与评分；
- 原始 NPZ、actor JSON 和报告位于外部 evidence 根目录，不进入 Git；
- 本阶段没有通过新鲜团队门，因此没有新宣传视频，也没有晋升组织者 actor。
